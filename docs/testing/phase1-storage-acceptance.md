# Phase 1 저장·변환 인수 검증 명세

출처: 2026-11-17 화요일(Asia/Seoul), 사용자 선택 및 저장·명시적 스키마 변환 문서화 계획 승인. 원본은 [저장 계약](../storage-contract.md), 연결 규칙은 [SQL 계약](../sql-contract.md)과 [스키마 계약](../schema-contract.md)이다.

**모든 사례는 미실행이다.** 아래는 Given/When/Then 명세이며 C 테스트 코드·Windows API 실행·DBMS 검증 통과가 아니다. 각 변형은 독립 실행하고 실패 지점은 실제 구현 시 테스트 대역으로 주입한다. CLI 인자·표시·진단·종료 코드는 [CLI 계약](../cli-contract.md)과 [CLI 인수 명세](phase1-cli-acceptance.md)를 따른다.

## 준비와 판정

- 기본 스키마는 users(id INT64, name TEXT, age INT64), orders(id INT64, amount INT64)다. 외부 JSON 구조와 ID·NULL 규칙은 기존 계약을 따른다.
- 일반 정상 시작에는 잠금·미해결 상태 없음·모든 스키마와 전체 데이터 파일 검증 성공이 필요하다.
- 파일 변경 없음은 원본 바이트/길이와 해독한 행을 모두 확인한다. 정상 반영은 별도 프로세스 재시작 후 조회까지 확인한다. 정렬 없는 SQL 결과는 행 다중집합으로 비교한다.
- 실패 판정은 문법/형식·스키마 불일치·값/변환·I/O·자원 부족·사용권 충돌·미해결 상태를 구분한다. 저장 오류에 없는 SQL 위치를 꾸며 넣지 않는다.
- 반영 확정 전 실패, 복원 실패, 확정 후 정리 실패를 구분한다. 확정 후 정리 실패는 SQL 성공·정리 오류·세션 중단이며 해당 SQL 재시도나 롤백이 아니다.

## 실행 연결

위 48개 사례는 모두 **미실행**이다. 향후 구현 시 각 ID에 실제 테스트 이름·명령·결과·증거를 연결한다. C 환경/import 실패를 기능 Red로 바꾸지 않는다. 문서 링크·ID 유일성·리뷰·Graphify/Wiki 검사를 실제 파일 반영·잠금·복구 검증으로 보고하지 않는다.
