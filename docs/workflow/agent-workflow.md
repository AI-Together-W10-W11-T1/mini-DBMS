# mini-DBMS 작업 흐름

Master 메인 1개와 Planner·Implementer·Reviewer_QA·Knowledge Manager 서브 4개, 총 5개의 논리 역할로 운영한다. 역할 수와 동시 실행 수는 다르다.

| 에이전트 | 책임 | 쓰기 범위 |
|---|---|---|
| Master | 사용자 협의·선택 기록, 배정, 결과 인수·반려, 최종 판단 | 운영 원장과 사용자 승인 기록 |
| Planner | 요구사항 분석, 설계 대안·GWT·구현/테스트 계획 | 소스 수정 없이 계획 결과 반환 |
| Implementer | 승인된 코드·테스트 구현, 실제 Red→Green→Refactor, 수정 작업 | 해당 작업에서 승인한 파일 |
| Reviewer_QA | 설계·코드·테스트 검토와 빌드·테스트 실행 | 소스 수정 없이 검토 결과와 검사 증거 반환 |
| Knowledge Manager | 검증된 설계 결정·실패·제한·결과 기록 | 해당 작업에서 승인한 Wiki·문서·작업 기록 |

사용자와 소통하는 창구는 Master뿐이다. 서브에이전트는 Master에게만 보고하고 다른 서브에이전트와 직접 통신하거나 재위임하지 않는다. Master가 필요한 원본 근거·계약·산출물·지적 사항을 전달한다. `.private` 자료는 서브에이전트에게 전달하지 않으며 개인 승인 원장은 Master가 관리한다.

한 작업은 다음 순서로 진행한다.

1. Master가 요구사항 `DBMS-001` 형식, 범위, 불변식, 실패 조건, 인수 기준을 정리한다.
2. Planner가 대안·계획·구체 테스트·변경 후보와 미결정을 반환한다.
3. Master가 확정 사항·이번에 선택할 사항·보류 사항, 대안의 장단점·권고안을 사용자에게 제시한다. 사용자가 선택한 계약과 변경 범위를 기록한 뒤 구현을 배정한다.
4. Implementer가 실제 기능 실패를 확인하고 최소 구현·리팩터링·회귀 검사·빌드를 수행한다. 환경/import 실패를 기능 Red로 보고하지 않는다.
5. Reviewer_QA가 고정된 구현을 검토하고 자신의 단계에서 최신 빌드·테스트를 실행한다. 코드 검토 결과와 실제 실행 결과를 구분해 반환하며 직접 코드를 수정하지 않는다.
6. Knowledge Manager가 인수된 검증 근거에 따라 승인된 문서만 갱신한다. 검증하지 않은 설계나 실행 결과를 사실로 기록하지 않는다.
7. Master가 결과·검사·한계·다음 선택을 사용자에게 보고한다. 사용자 확인 뒤 완료 처리한다.

새로운 선택이나 범위 변경이 생기면 해당 작업을 멈추고 Master가 사용자와 상의한다. 이미 승인한 범위를 그대로 실행하는 데 같은 승인을 반복 요구하지 않는다. 영향 없는 독립 작업은 계속할 수 있다.

같은 작업의 의존 단계는 순차로 지킨다. 독립적인 run은 파일 읽기/쓰기 범위·공유 자원·사용자 승인 상태가 충돌하지 않을 때 병렬 실행한다. 예를 들어 현재 구현의 검증과 다음 기능의 독립 조사, 현재 구현과 이전 완료 작업의 기록을 겹칠 수 있다. 같은 작업의 구현과 검증은 겹치지 않는다. 공유 파일을 쓰는 작업은 Master가 직렬화한다.

품질 반려는 같은 작업 기준으로 누적한다. 지적 ID가 달라도 같은 작업의 반려 횟수에 포함하며 한 번의 검토에 여러 지적이 있어도 1회다. 두 번째 반려 후 Master가 원인을 재검토하고 수정 조건을 구체화한다. 세 번째 반려 시 자동 재지시를 멈추고 Master가 시도 내역·남은 문제·원인 추정·선택지를 사용자에게 보고한다. 환경 장애나 요구사항 변경은 별도로 기록한다.

구현 언어 C, 표준 C23, 실행 환경 Windows 네이티브는 확정했다. 공식 LTS 우선, 없는 경우 최신 안정판을 버전 고정하는 정책과 cmocka·CTest 테스트 구성 방향을 채택했다. 기존 추천 조합의 도구 설치·C23 실행 검증·실제 명령 연결은 아직이다. Python은 운영 스크립트 실행용이다. 하네스의 build 검사는 실제 C 컴파일·링크 성공을 확인한다.

[요구사항](../requirements.md)에 따라 Phase 1 SQL 처리기 → Phase 2 메모리 B+ 트리·100만 건 이상 비교 → Phase 3 API·Thread Pool 순서로 이전 결과물을 재사용한다. [Phase별 상세 설계 원칙](../phase-design-policy.md)에 따라 모듈을 과도하게 나누지 않고 현재 Phase의 상세 설계만 사용자와 확정한다. 후속 Phase는 연계 요구사항만 기록하고 저장 포맷·API·스레드 구조 등을 지금 결정하지 않는다. Phase별 설계 전용 하네스 경로는 다음 구현 계획에 포함할 미구현 작업이다.

도구와 검토 기준이 모두 정해지면 Master가 준비 상태를 보고한다. Plan 모드와 Goal은 사용자가 이후 직접 시작하며 현재 미리 생성하지 않는다.
