# Phase별 상세 설계와 검토 원칙

전체 목표와 Phase 간 재사용 요구사항은 [요구사항](requirements.md)에 기록한다. 전체 상세 설계는 지금 고정하지 않는다. 현재 Phase의 요구사항을 만족하는 작고 설명 가능한 설계를 먼저 만들고, 다음 Phase에 들어갈 때 상세 설계를 다시 검토한다.

## 진행 단위

1. Planner가 현재 Phase의 범위·대안·장단점·미결정·GWT·구현/테스트 계획을 정리한다.
2. Master가 확정/선택/보류를 사용자에게 보고하고 사용자 선택을 받는다.
3. Reviewer_QA가 선택한 설계와 검증 계획을 검토한다. 새 선택이 필요하면 Master를 통해 사용자에게 돌아간다.
4. Knowledge Manager가 승인된 결정을 기록한다. 사용자 최종 확인 뒤 해당 Phase의 구현 계약으로 연결한다.
5. Implementer가 승인 범위를 구현하고 Reviewer_QA가 코드 검토·실제 빌드·기능 검증을 수행한다.
6. 검증 결과·한계·후속 Phase에 남길 선택을 사용자에게 보고한다.

다음 Phase는 앞 단계 결과물을 재사용한다. 필요한 연계 조건은 남기되 미래 Phase의 API·파일 형식·스레드 구조를 미리 확정하지 않는다. 기존 계약 변경이 필요하면 이유와 영향을 설명하고 사용자와 상의한다.

## 검토 범위

- 현재 Phase의 요구사항·포함/제외·완료 조건이 명확한지.
- 대안의 장단점·선택 이유·아직 결정하지 않은 부분이 드러나는지.
- 소수의 모듈로 책임을 설명할 수 있는지. 모듈·파일의 개수와 이름은 설계 시 정하고 불필요한 계층을 추가하지 않는다.
- C API·자료 구조·데이터 소유권과 수명·메모리 해제·오류 반환이 일관되는지.
- 해당 Phase에 필요한 저장·검색·파일 처리·일관성 조건이 명확한지.
- Windows·C23에서 구현 가능하고 단위/기능/엣지 테스트로 검증 가능한지.
- 후속 Phase의 기존 처리기·엔진 재사용 요구사항을 막는 결정이 있는지.

Phase 2에서는 메모리 B+ 트리와 100만 건 이상 비교 조건을 상세화한다. Phase 3에서는 API·Thread Pool·동시성 검증을 상세화한다. 사용자가 요구하지 않은 성능 목표·트랜잭션·WAL·복구 기능은 자동으로 추가하지 않는다.

## 설계 검토와 실제 검증의 구분

설계 단계 산출물은 현재 Phase의 설계 문서·결정표·인터페이스·GWT/테스트 계획이다. 설계 검토만으로 실제 빌드·기능·성능 검증이 통과했다고 보고하지 않는다.

현재 하네스는 실제 Red/build/QA를 요구하는 구현 작업용이다. Phase별 설계 전용 완료 경로는 아직 미구현이며 다음 구현 계획에서 지원할 작업이다. 구현용 게이트를 형식적으로 우회해 설계 작업을 DONE 처리하지 않는다.

Plan 모드와 Goal은 사용자가 직접 시작한다. 이번 요구사항 기록으로 Goal을 생성하거나 Phase 1 설계·구현을 미리 시작하지 않는다.
