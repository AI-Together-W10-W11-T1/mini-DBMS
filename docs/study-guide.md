# mini-DBMS 학습 가이드

2026-11-19 목요일(Asia/Seoul). 현재 **Phase 1의 SQL·파일 저장(M1~M8), Phase 2의 B+ 트리·100만 행 벤치마크(M9~M11), Phase 3의 서버·C SDK·병렬 읽기·배타 쓰기·협력 취소·서버 성능 측정(M12~M14)**까지 구현하고 독립 QA와 사용자 최종 완료 승인을 마쳤습니다. 최종 전체 회귀는 **198/198 통과**입니다. 구현 완료와 운영 용량 보장·미검증 한계는 구분합니다. 현재 상태는 [HANDOFF](../HANDOFF.md), 실제 검사와 한계는 [M13 결과](testing/m13-results.md)·[M14 결과](testing/m14-results.md)를 따릅니다.

아래는 공부할 주제별로 **우리가 택한 방식 → 비교할 선택지 → 코드에서 확인할 질문**을 정리한 표입니다. 비교란의 선택지는 학습용 비교도 포함하며, 모두 실제 채택 후보로 검토했다는 뜻은 아닙니다.

## Phase 1 — SQL 처리기와 파일 저장

| 공부할 주제 | 우리가 택한 방식 | 비교할 선택지와 공부할 질문 |
| --- | --- | --- |
| **1. C 빌드 도구** | Windows 네이티브 C23, LLVM/Clang, CMake, Ninja, LLDB. 단위 테스트는 cmocka, 테스트 실행은 CTest | GCC와 Clang, GDB와 LLDB는 각각 어떤 역할이 겹치나? CMake가 구성하고 Ninja가 빌드한다는 건 무슨 뜻인가? |
| **2. 엔진과 CLI의 경계** | 공용 C 엔진에 SQL·스키마·저장 로직을 두고, CLI는 입력과 출력 담당 | CLI 안에서 모든 작업을 처리하면 나중에 서버에서 무엇을 재사용하기 어려워지나? |
| **3. 스키마 제공** | 테이블별 외부 JSON. 디렉터리 바로 아래 JSON을 시작 시 찾아 읽고 검증. 파일명과 테이블명은 일치해야 함 | C 코드에 고정 vs JSON 한 파일 vs 테이블별 JSON. 폴더 전체 검색과 별도 목록 파일은 관리 부담이 어떻게 다른가? |
| **4. JSON 파싱·인코딩** | yyjson과 엄격한 UTF-8 JSON 규칙. 파싱 후 이름·타입·중복·ID 규칙을 따로 검사 | cJSON과의 차이는 무엇인가? 깨진 UTF-8, 잘못된 JSON, 올바른 JSON에 들어 있는 잘못된 컬럼 정의는 각각 어디서 잡나? |
| **5. SQL 파싱** | UTF-8 SQL 파일에서 문장 경계를 찾고, 파싱 → 이름·타입 검증 → 실행. 마지막 세미콜론 필수 | 왜 `split(';')`만으로는 `INSERT ... VALUES ('a;b');`를 처리할 수 없나? 파일 중간에 오류가 나면 왜 앞선 성공은 유지하나? |
| **6. 타입과 이름** | 저장 타입은 `INT64`·`TEXT`, 값은 `NULL` 가능하되 ID는 예외. 암묵적 타입 변환 없음. ASCII 식별자는 대소문자를 무시하고 데이터 문자열은 보존 | 인용 식별자, 실수, `VARCHAR` 등으로 범위를 넓히면 파서·비교·저장 중 어디가 바뀌나? `NULL`, 빈 문자열, 숫자 `0`은 어떻게 구별하나? |
| **7. INSERT·UPDATE·DELETE** | INSERT 컬럼 목록 필수, 복수 행 허용. UPDATE·DELETE는 WHERE 필수. ID 수정 금지. UPDATE 결과 건수는 **조건에 일치한 행 수** | 컬럼 목록 생략, WHERE 생략, 값이 실제 바뀐 행만 세는 정책과 비교. `SET name = name`이 왜 1건으로 나올 수 있나? |
| **8. SELECT·조건·JOIN** | 컬럼 선택, 비교, `AND`·`OR`, `IS NULL` 지원. 두 테이블 등호 `INNER JOIN`은 중첩 루프로 실행 | 해시 조인으로 바꾸면 시간과 메모리가 어떻게 달라지나? 두 입력에 모두 `id`가 있으면 `SELECT id`를 왜 거절하나? |
| **9. GROUP BY·COUNT** | 입력 컬럼만 그룹 키로 사용. 그룹을 선형으로 찾아 집계. `COUNT(*)`는 전체 행, `COUNT(col)`은 NULL이 아닌 행을 셈. 기본 이름은 `count_all`, `count_<컬럼명>` | 출력 별칭을 GROUP BY에 허용할지, COUNT에 `AS`를 강제할지, 해시로 그룹을 찾을지 비교. `NULL = NULL`과 NULL끼리 같은 그룹이 되는 규칙은 어떻게 공존하나? |
| **10. ORDER BY·페이지** | 여러 출력 컬럼으로 정렬. ASC·DESC 모두 기본 NULL 마지막, 키별 변경 가능. **FETCH FIRST는 정렬 없이 가능, OFFSET은 ORDER BY 필수** | 둘 다 정렬 필수 또는 둘 다 선택으로 두는 방식과 비교. `ORDER BY score`에서 동점이 많으면 페이지를 고정하려고 왜 `id` 같은 고유 키를 추가하나? |
| **11. VALUES·UNION** | 독립 VALUES는 결과만 생성. UNION은 전체 행 중복을 제거하고 UNION ALL은 보존. 여러 분기는 왼쪽부터 결합하고 정렬·페이지는 최종 결과에 적용 | 분기별 정렬을 허용하면 문법과 이름 해석이 어떻게 복잡해지나? 같은 ID에 다른 이름을 가진 두 행은 UNION에서 왜 둘 다 남나? |
| **12. 실제 행 저장 형식** | 테이블별 가변 길이 바이너리 파일. 헤더로 컬럼 이름·타입·순서를 확인 | CSV·JSONL·바이너리 비교. NULL과 빈 문자열을 어떻게 구분하나? 같은 타입인 컬럼 둘의 순서를 바꾸면 헤더가 왜 필요한가? |
| **13. 파일 변경과 실패 처리** | INSERT는 뒤에 추가하고 실패하면 이전 파일 길이로 복원. UPDATE·DELETE는 임시 파일에 결과를 완성한 뒤 교체 | 모든 변경마다 전체 파일 교체, 제자리 수정, 삭제 표시 후 나중에 정리하는 방식과 비교. 문장 도중 복원 가능한 쓰기 실패와 전원 차단은 왜 다른 문제인가? |
| **14. init·잠금·검증** | `init`으로 빈 데이터 파일을 명시적으로 만들고, 일반 실행 중 파일 누락은 오류. 한 데이터 디렉터리는 한 프로세스가 소유. 시작 시 저장 행 전체를 검사 | 첫 INSERT에서 자동 생성하거나 첫 테이블 사용 시 행을 검사하는 방식과 비교. **0행인 파일**과 **파일이 없음**을 왜 구분하나? |
| **15. 스키마 변경** | 일반 실행은 불일치를 거절. `migrate`는 같은 테이블 집합을 새 데이터 디렉터리에 복사·변환하고 ID와 원본을 보존 | 기존 파일 교체, 테이블 추가·제외까지 지원하는 방식과 비교. 컬럼 하나를 바꿀 때 나머지 테이블 파일은 새 디렉터리에서 어떻게 준비되나? |
| **16. CLI 입출력** | `init`·`run`·`migrate`. SQL 파일 또는 명시적 stdin, 기본 표 또는 선택 JSONL. 스키마·데이터 경로 명시, 오류는 stderr | 파일만 지원, `-e "SELECT ..."` 같은 인라인 SQL, 기본 경로 사용과 비교. 사람이 보는 표와 프로그램이 읽는 JSONL은 왜 둘 다 필요한가? |

원본과 실행 예제는 [SQL 계약](sql-contract.md), [스키마 계약](schema-contract.md), [저장 계약](storage-contract.md), [CLI 계약](cli-contract.md), [README](../README.md)에 있습니다. 구현 흐름은 [SQL](../src/sql.c)·[스키마](../src/catalog.c)·[저장](../src/storage.c)·[CLI](../src/cli.c)에서 확인할 수 있습니다.

## Phase 2 — 자동 ID, B+ 트리, 성능 비교

| 공부할 주제 | 우리가 택한 방식 | 비교할 선택지와 공부할 질문 |
| --- | --- | --- |
| **17. ID 발급과 수명** | 초기 Phase 1은 양의 ID 직접 입력만 지원했다. 현재는 Phase 2에서 추가한 자동 발급으로 ID 생략 시 현재 최댓값+1을 사용하며, 양의 ID 직접 지정도 허용. 빈 테이블은1부터 시작하고 ID 수정은 금지 | 0부터 시작할지, 직접 입력만 받을지, 별도 발급 카운터를 저장할지 비교. `id` 생략과 `id=NULL`이 왜 다른가? 최댓값 행을 삭제하면 이후 발급 규칙에 어떤 영향이 있나? |
| **18. 리프에 저장하는 값** | **현재 코드의 리프는 `ID → 메모리 행 번호`를 저장.** 파일 바이트 위치를 저장하는 방식은 다른 설계다. | 행 전체, 파일 오프셋, 메모리 행 번호 중 무엇을 저장할 수 있나? 행 번호가 밀리면 기존 인덱스 항목은 어떻게 되나? |
| **19. 트리 용량과 분할** | 실행용은 내부 자식 32·경계 키 최대 31·리프 항목 31. 테스트용은 자식 4·경계 키 최대 3·리프 항목 3. 경계 키는 오른쪽 서브트리의 최소 키 | 왜 자식 32개에 경계가 31개인가? 왜 리프 분할에선 경계 키를 부모에 복사하고, 내부 노드 분할에선 경계 키를 위로 올리는가? |
| **20. 인덱스와 파일의 일관성** | 시작 시 행을 검증하며 인덱스 생성. INSERT는 노드를 미리 예약하고 파일 반영 뒤 인덱스 공개. UPDATE는 ID·행 순서가 유지되어 인덱스 재사용. DELETE는 행이 압축되므로 새 인덱스 준비 | DELETE마다 기존 트리 항목만 지우면 왜 부족한가? 파일을 쓴 **뒤에** 인덱스 메모리 할당이 실패하면 어떤 상태가 되는가? |
| **21. 인덱스를 쓰는 SQL 조건** | 단일 테이블 `id = 정수`에서 사용. AND 안의 필수 ID 등식으로 후보를 좁힌 뒤 전체 WHERE를 다시 검사. OR·JOIN·범위 조건은 기존 스캔 경로 | `id = 25 AND name = 'Kim'`과 `id = 25 OR name = 'Kim'`에서 `id=25` 후보만 확인하면 어떤 차이가 생기나? |
| **22. 벤치마크 설계** | 재현 가능한 SQL을 생성해 CLI에서 1만 행씩 적재. 1만·10만·100만 행의 데이터 정확성을 검증하고, DB를 연 뒤 같은 공개 엔진 API에서 `id` 조회와 `scan_key` 선형 탐색을 비교 | SQL 파싱·시작·적재·실제 조회 시간을 한 숫자로 합치면 무엇을 알기 어려워지나? 중앙값 p50과 느린 쪽 p95는 각각 뭘 보여주나? |

100만 행 **Debug·적재 후 warm 상태**에서 조회 p50은 ID **37.2µs**, 선형 탐색 **15.67ms**로 약 **421배** 차이였어요. DB를 여는 데 든 **약 118.7초**는 별도 측정이고 원인은 아직 진단하지 않았어요. 공부할 때 `O(log n)` 대 `O(n)`이라는 연산 모델과 이 실행에서 관측한 시간 차이를 함께 보면 돼요. ## Phase 3 — 서버, SDK, 동시성

| 공부할 주제 | 우리가 택한 방식 | 비교할 선택지와 공부할 질문 |
| --- | --- | --- |
| **23. 서버 사용 형태** | 서버 실행 파일 + 헤더·정적 C SDK + SDK를 쓰는 원격 CLI. 기존 엔진 재사용 | 원격 CLI가 소켓을 직접 다루는 구조와 비교. 연결·전송·응답 해석을 SDK에 두면 다른 C 프로그램에서 무엇을 재사용할 수 있나? |
| **24. 통신 프로토콜** | 길이 프레임을 붙인 TCP+JSON. 한 요청에 복수 SQL을 담고 문장별 결과·오류·완료 상태를 전달 | TCP에서 한 번 `send`한 크기와 한 번 `recv`한 크기가 왜 다를 수 있나? 프레임 길이를 먼저 읽으면 어떻게 메시지 경계를 찾나? |
| **25. 네트워크 루프와 Thread Pool** | 네트워크 루프가 소켓을 맡고 SQL은 워커 풀에 전달. M12에서는 엔진 실행을 직렬화했고, **현재 M13 구현은 DB gate로 병렬 읽기·배타 쓰기를 지원** | 연결마다 스레드를 쓰는 구조와 비교. 소켓 여러 개를 동시에 처리하는 것과 여러 SQL이 엔진 안에서 동시에 실행되는 것은 어떻게 다른가? |
| **26. 응답 크기와 자원 제한** | 완성한 결과 JSON을 바이트 단위로 나누어 보내고 SDK에서 재조립. 접속·워커·대기열·프레임 크기·시간 제한을 구분 | 행을 만들 때마다 보내는 스트리밍과 비교. 프레임을 작게 잘라도 서버가 결과를 먼저 전부 만들면 왜 최대 메모리 사용량이 그대로 클 수 있나? |
| **27. 실패와 다음 문장** | 첫 SQL 오류에서 멈추고 이전 성공은 보존. 연결 종료를 감지하면 후속 문장을 중단. SDK는 반영 여부를 알 수 없는 상태를 표현 | 서버가 INSERT를 반영한 직후 응답 전에 연결이 끊기면, 클라이언트가 재시도할 때 왜 중복이 생길 수 있나? |
| **28. 읽기·쓰기 동시성** | DB 소유 gate가 SELECT·VALUES·조회 UNION은 공유 읽기, INSERT·UPDATE·DELETE는 배타 쓰기로 실행. **쓰기가 기다리면 새 읽기 진입을 차단**. 엄격 FIFO나 모든 요청의 기아 방지는 보장하지 않음 | 읽기 우선과 쓰기 대기 우선은 어떤 부하에서 유리한가? 읽기가 빌린 TEXT·인덱스를 쓰는 동안 writer가 바꾸면 무엇이 깨지나? 결과를 소유 복사한 뒤 gate를 풀어야 하는 이유는? |
| **29. 대기·SQL 기한** | queue 기한은 등록→워커 인수, lock 기한은 한 문장의 실제 gate 대기 누적, SQL 기한은 최종 gate 취득 뒤 의미 검증·실행부터 계산. `--sql-timeout-ms` 기본0은 비활성, 양수는 안전 지점의 협력 취소 | 큐 대기·잠금 대기·SQL 실행 시간을 왜 분리하나? gate 재취득 때 budget을 초기화하면 어떤 문제가 생기나? 협력 기한이 단일 OS I/O의 즉시 중단을 보장하지 않는 이유는? |

M14 실제 실행은 **37회**입니다. 원래36회 중35개가 유효했고, 큐 시각이9QPC ticks(0.9µs) 역행한1개는 무효 원본으로 보존했습니다. 같은 조건 재측정1개를 더해 선택한36개 자료와 최종36만 행을 검증했습니다. 실측19,080시도 중13,301성공·`SERVER_BUSY`5,779건이며 warmup 오류는 별도입니다. 최종 전체 회귀198개는 독립 QA 지시·평가 아래 정확히1회 통과했습니다. 실제 로컬 TCP 검사 호출은 Master가 보조했습니다. 자세한 실행 귀속·실패·수정·한계는 [M14 결과](testing/m14-results.md)를 따릅니다.

공부할 때는 **행 하나를 끝까지 추적**해 보는 게 좋아요. `INSERT`에서 ID가 발급되고 **파일·메모리 행·인덱스**에 각각 무엇이 들어가는지 본 다음, `SELECT ... WHERE id = 25`가 **파서 → B+ 트리 → 메모리 행 → 출력**을 어떻게 통과하는지 따라가세요. 마지막으로 같은 SQL을 원격 CLI에서 보내면 그 앞뒤에 **TCP 프레임·워커·SDK**가 어떻게 붙는지 연결해서 볼 수 있어요.

원격 경로에서는 **gate 진입·쓰기 대기·안전 지점 취소·저장 보호구간**을 추가로 따라가세요. 마지막으로 측정 기록에서 **큐 등록→워커 인수 대기**, **gate 대기**, **SQL 실행**, **EOF 확인 작업**이 서로 다른 구간임을 구분해 보세요. M14가 직접 수치화한 것은 큐 대기이며 gate 대기 수치는 아직 측정하지 않았습니다. 시작 비용 진단·설정 조합 비교·성능 조정은 [후속 선택](pending-decisions.md)으로 남아 있습니다.
