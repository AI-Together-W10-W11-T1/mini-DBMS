# 미니 DBMS 요구사항

출처: 현재 대화에서 사용자가 제공한 과제 요구사항과 운영 원칙. 이 문서는 요구사항을 정리한 것이며 상세 구현 설계를 확정한 문서가 아니다.

## 단계와 연계

| 단계 | 의존 | 필수 결과물 |
|---|---|---|
| Phase 1 | 없음 | CLI로 SQL 파일을 받아 INSERT/SELECT를 수행하는 파일 기반 SQL 처리기 |
| Phase 2 | Phase 1 | 기존 처리기 + 메모리 기반 B+ 트리 인덱스 + 100만 건 이상 성능 비교 |
| Phase 3 | Phase 1 + Phase 2 | 기존 엔진을 감싼 외부 호출 가능한 API 서버 + Thread Pool 병렬 처리 |

Phase 2는 Phase 1 SQL 처리기를 그대로 활용한다. Phase 3은 Phase 1과 Phase 2를 내부 DB 엔진으로 활용한다. 재사용 요구사항은 유지하되 전체 상세 설계를 한 번에 고정하지 않는다.

## Phase 1 — SQL 처리기

- 텍스트 파일에 작성한 SQL을 Command Line 명령으로 처리기에 전달할 수 있어야 한다.
- SQL을 읽고 파싱해 구조화한 뒤 실행한다. 최소 지원 문장은 INSERT와 SELECT다.
- INSERT는 해당 테이블 파일에 데이터를 추가한다.
- SELECT는 테이블 파일의 데이터를 읽어 출력한다.
- 테이블마다 파일로 관리한다. 저장 형식의 원래 선택 범위는 CSV·binary·custom 등이며, 후속 합의로 가변 길이 바이너리를 채택했다. 파일 구조·변경 처리는 [저장 계약](storage-contract.md)을 따른다.
- schema와 table은 이미 존재한다고 가정한다. CREATE TABLE은 필수가 아니다. 외부 JSON의 테이블별 스키마와 시작 시 전체 검증은 [스키마 계약](schema-contract.md)을 따른다.
- 핵심 흐름은 입력(SQL) → 파싱 → 실행 → 저장/조회다.

## Phase 2 — B+ 트리 인덱스

- 실제 디스크 기반 B+ 트리를 단순화한 메모리 기반 B+ 트리를 구현한다.
- 테이블에 레코드를 추가하면 ID를 자동 부여하고 B+ 트리에 해당 ID를 등록한다.
- ID 기반 검색 시 B+ 트리 인덱스를 사용한다. WHERE id = ? 조건에서 인덱스를 적용하는 흐름을 검토한다.
- 최소 1,000,000개 이상의 레코드를 삽입한다.
- ID 기준 SELECT의 인덱스 검색과 다른 필드 기준 SELECT의 선형 검색 속도를 비교한다.
- 대량 레코드를 쉽게 생성·삽입·검증할 방법을 마련한다.
- Phase 1 처리기와 연동한다. 인덱스가 가리킬 레코드 위치 표현·재시작 시 처리·B+ 트리 세부 구조는 Phase 2 설계에서 정한다.

## Phase 3 — API 서버

- 외부 클라이언트가 API를 호출해 DBMS 기능을 사용할 수 있어야 한다.
- Thread Pool을 구성하고 요청에 스레드를 할당해 SQL 요청을 병렬 처리한다.
- Phase 1 SQL 처리기와 Phase 2 B+ 트리 인덱스를 내부 엔진으로 활용한다.
- 멀티스레드 동시성 문제와 내부 엔진·외부 API 연결을 설계하고 검증한다.
- 같은 데이터 디렉터리는 한 번에 하나의 DBMS 프로세스만 연다. 다른 데이터 디렉터리는 동시에 사용할 수 있다. 서버 프로세스 내부의 작업 스레드는 엔진을 공유하며 파일·인덱스 변경을 내부 동기화한다. 세부 잠금 설계는 Phase 3에서 정한다.
- API 프로토콜·요청/응답 형식·스레드 수·큐·동기화 방식은 아직 선택하지 않았다. HTTP/REST/JSON 등을 필수 요구사항으로 추가하지 않는다.

## 공통 품질과 학습 원칙

- 구현을 우선해 실제 동작하는 결과물을 만든다. AI를 적극 활용할 수 있으며 전체 코드 생성도 허용한다.
- 생성된 코드를 학습하고 핵심 로직의 원리와 동작을 이해·설명할 수 있어야 한다.
- 단위 테스트로 함수를 검증하고 가능한 엣지 케이스를 고려한다.
- Phase 1은 SQL 처리 기능 테스트를 수행한다.
- Phase 2는 B+ 트리의 정확성과 인덱스 사용/미사용 성능 차이를 검증한다.
- Phase 3은 실제 API 서버를 준비해 기능 테스트를 수행한다.
- 이력서·포트폴리오에 포함할 수 있는 완성도를 목표로 한다.
- 다른 팀과 차별화할 추가 요소는 후보와 효과를 사용자에게 제안하고 선택 후 범위에 넣는다.

## 현재 확정한 구현 조건

- 언어 C, 표준 C23, 실행 환경 Windows 네이티브.
- 공식 LTS를 우선하고, 없는 도구는 최신 안정판을 버전 고정해 사용한다.
- 테스트 구성은 cmocka 채택과 CTest 실행·집계 방향이다. 라이선스·배포 기록은 Master가 관리한다.
- 모듈을 과도하게 나누지 않는다. 모듈 수·파일 수·경계는 아직 정하지 않았다.
- 상세 설계는 Phase 하나씩 사용자와 확정한다. 전체 상세 설계를 지금 일괄 고정하지 않는다.
- 실제 도구 설치·C23 기능 검증·빌드/테스트 명령 연결·DBMS 구현은 아직 완료하지 않았다.

## Phase 1 상세 설계에서 선택할 사항

SQL 부분집합과 동작은 후속 사용자 협의에서 확정했다. 원본 과제의 최소 조건에 다음 기능을 추가한다: UPDATE/DELETE, 6종 비교·AND/OR·NULL, 다중 정렬·OFFSET/FETCH FIRST, 두 입력 INNER JOIN/self-join, COUNT/GROUP BY/HAVING, 독립 VALUES, UNION/UNION ALL. 정확한 계약은 [SQL 계약](sql-contract.md), 성공·오류·경계 검증은 [인수 명세](testing/phase1-sql-acceptance.md)를 따른다. 상세 기능은 Phase 1 내부에서 의존 순서로 구현하며 Phase 2로 이월하지 않는다.

- 기존 schema/table은 테이블별 외부 JSON 파일로 제공한다. 이름·타입·순서와 엄격한 시작 검증은 [스키마 계약](schema-contract.md), 검증 조건은 [스키마 인수 명세](testing/phase1-schema-acceptance.md)를 따른다. JSON 파서는 yyjson 0.13.0 소스 포함 방침이며 실제 반입·빌드는 아직이다.
- SQL 문법·자료형·리터럴·오류 처리는 확정 SQL 계약을 따른다. 이 항목을 다시 미정으로 취급하지 않는다.
- 저장은 테이블별 가변 길이 바이너리, INSERT 추가 쓰기와 UPDATE·DELETE 임시 파일 교체 혼합 방식이다. 명시적 초기 준비, 시작 시 전체 데이터 검증, 미해결 변경 표식에 의한 재시작 차단은 [저장 계약](storage-contract.md), 검증 조건은 [저장 인수 명세](testing/phase1-storage-acceptance.md)를 따른다.
- 일반 실행은 스키마 불일치를 거절하며 사용자가 명시적으로 요청한 변환만 수행한다. 같은 테이블 집합에서 비ID 컬럼 추가·재배열·이름 변경·삭제·타입 변환을 지원한다. 새 데이터 디렉터리 전체를 복사·변환·검증하고 원본은 보존한다. ID는 이름·타입·값을 유지한다. TEXT→INT64는 양끝 ASCII 공백·탭·CR·LF 제거 후 엄격한 십진수·범위 검사를 한다. 일반 SQL의 암묵적 타입 변환 금지 계약은 유지한다.
- CLI는 `init`·`run`·`migrate`, 필수 스키마/데이터 경로, 파일 또는 명시적 stdin 입력(기본 REPL 아님), 기본 표/선택 JSONL로 확정했다. stdout 성공 결과와 stderr 진단, 종료 코드·실패 우선순위는 [CLI 계약](cli-contract.md), 검증 조건은 [CLI 인수 명세](testing/phase1-cli-acceptance.md)를 따른다.
- 테스트 데이터·인수 조건·실패 및 엣지 케이스와 최소 모듈 경계.

SQL·스키마·저장·변환·CLI 계약은 확정했다. 다음 구현 계획에서 최소 C API·모듈 경계, 테스트 데이터와 실제 검사 연결, 도구 설치/C23 검증 및 설계 전용 하네스 경로를 구체화해야 한다. Phase 1 상세 설계 전체가 준비됐다는 뜻은 아니다. 인수 명세는 검증 요구이며 자동 테스트 통과를 뜻하지 않는다. 실제 C 구현·빌드·기능 검사는 후속 작업이다. 진행 표식에 의한 실행 차단은 강제 종료·전원 차단 자동 복구 보장이 아니다. 벤치마크는 한 DBMS 프로세스에서 적재와 조회 비교를 수행한다.
