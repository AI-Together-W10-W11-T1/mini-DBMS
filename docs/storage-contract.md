# Phase 1 저장·명시적 스키마 변환 계약

출처: 2026-11-17 화요일(Asia/Seoul), 현재 대화의 저장·변환 선택과 확정·문서화 계획에 대한 `Implement the plan` 승인. 이 문서는 구현할 계약이며 **C 구현·Windows 파일 API 실행·자동 기능 검사는 아직 없다.** 검증 요구는 [저장 인수 명세](testing/phase1-storage-acceptance.md), SQL 의미는 [SQL 계약](sql-contract.md), 외부 정의는 [스키마 계약](schema-contract.md)을 따른다.

## 1. 파일 집합과 시작

- 실제 행은 테이블별 가변 길이 바이너리 파일에 저장한다. 외부 스키마는 기존 JSON 방식을 유지한다.
- 데이터 파일명은 `table_<ASCII 소문자로 접은 테이블명>.tbl`이다. 예: `Users` → `table_users.tbl`. 접기는 이름 식별에만 사용하고 결과 이름의 원철자는 외부 스키마에서 보존한다.
- 데이터 디렉터리마다 실제 프로세스 사용권을 획득한다. 같은 디렉터리는 한 DBMS 프로세스만 열고, 다른 디렉터리는 동시에 사용할 수 있다. 일반 실행·초기 준비·변환 모두 이 규칙을 따른다.
- 사용권은 Windows 파일 handle의 공유 거부로 유지한다. 잠금 파일의 단순 존재를 잠금으로 간주하지 않으며 handle은 작업 수명 동안 유지하고 상속하지 않는다. 별칭 경로로 같은 디렉터리를 열어도 중복 사용을 허용하지 않는다.
- 일반 시작은 미해결 진행 표식과 엔진 작업 잔여물을 먼저 검사한다. 있으면 행 전수 검사 결과가 정상이어도 실행을 차단한다. 임의 삭제·자동 복구로 진행하지 않는다.
- 스키마 전체 검증 후 데이터 파일의 존재·헤더·스키마 호환성과 **모든 행**의 길이·타입·UTF-8·ID 제약을 검증한다. 필요한 파일 누락이나 잘못된 파일을 빈 테이블로 대체하지 않는다.
- 한 파일이라도 실패하면 SQL을 시작하지 않는다. 전수 검증은 스키마·데이터 준비 단계이며 SQL 파일 전체 사전 검증이 아니다. SQL은 기존 문장별 실행·첫 오류 중단·앞선 성공 유지 계약을 따른다.
- 저장 파일은 이진 I/O로 읽고 쓰며 Windows 텍스트 모드의 줄바꿈 변환을 적용하지 않는다. 실행 중 외부 프로그램이 데이터 파일을 수정하는 사용은 지원 계약에 포함하지 않는다.

## 2. 바이너리 포맷 1

모든 정수 필드는 little-endian이다. C 구조체의 padding·포인터·ABI를 파일에 복사하지 않는다.

| 순서 | 항목 | 바이트 계약 |
|---|---|---|
| 1 | 매직 | ASCII `MINIDBMS` 정확히 8바이트 |
| 2 | 저장 포맷 버전 | UINT32, 값 1 |
| 3 | 스키마 JSON 길이 | UINT64, 뒤따르는 JSON의 바이트 수 |
| 4 | 스키마 JSON | 길이만큼의 UTF-8 JSON. 외부 스키마와 같은 `version`·`name`·`columns` 구조이며 BOM 없이 기록 |
| 5 | 레코드 | 아래 레코드 구조를 EOF까지 반복 |

저장 포맷 버전과 JSON의 스키마 `version`은 별개 항목이다. 둘 다 현재 1만 허용한다. 헤더만 있는 파일은 0행 테이블이다. 저장 헤더의 JSON에도 엄격한 구조·이름·ID 스키마 검증을 적용한다.

| 레코드 구성 | 표현 |
|---|---|
| 본문 길이 | UINT64. 이 길이 필드 8바이트를 제외한 본문의 바이트 수 |
| 필드 순서 | 헤더의 컬럼 배열 순서. 별도 정렬·padding 없음 |
| NULL 필드 | 태그 0 한 바이트. 뒤에 값 payload 없음 |
| 비NULL INT64 | 태그 1 한 바이트 + 2의 보수 INT64 8바이트 |
| 비NULL TEXT | 태그 1 한 바이트 + 바이트 길이 UINT64 + 원본 UTF-8 바이트 |

- 태그는 0과 1만 허용한다. 타입은 스키마에서 결정하며 행에 중복 타입 태그를 추가하지 않는다.
- 빈 TEXT는 태그 1·길이 0이며 NULL과 다르다. 한글·작은따옴표·쉼표·세미콜론·실제 CR/LF 바이트를 보존한다.
- 본문을 정확히 컬럼 수만큼 해독했을 때 소비 바이트 수가 본문 길이와 같아야 한다. 부족·초과·잘린 길이 필드·잘린 payload를 거절하며 마지막 불완전 행을 무시하지 않는다.
- 길이 합산·offset 계산의 오버플로, 파일 남은 길이, 호스트 메모리 크기 변환을 할당·읽기 전에 검사한다. Windows 파일 위치는 INT64 비음수 범위 안에서 처리한다. UINT64 길이를 검증 없이 signed 값이나 `size_t`로 축소하지 않는다.
- ID의 INT64·필수·양수·테이블별 고유 제약은 모든 저장 행에도 적용한다. ID는 배열 중간에 있어도 이름으로 찾는다.
- INSERT가 앞부분을 수정하지 않도록 행 수·최신 ID 같은 가변 카운터를 헤더에 두지 않는다. 파일의 영속 행 수는 유효 레코드들을 읽어 판단한다.
- 이 포맷은 프레임·타입·UTF-8·ID 오류를 검사하지만 모든 비트 손상을 탐지하는 체크섬·복구 포맷을 약속하지 않는다.

## 3. 스키마 호환과 명시적 초기 준비

- 일반 실행은 헤더의 테이블명·컬럼명·타입·순서를 외부 스키마와 대조한다. 이름은 기존 ASCII 대소문자 무시 규칙으로 비교한다. 대소문자만 달라졌으면 호환이다.
- 컬럼 수·이름·타입·순서 중 하나라도 달라지면 일반 실행은 거절하고 파일을 보존한다. 같은 타입 컬럼끼리 재배열한 경우도 감지한다.
- 초기 준비는 사용자가 명시적으로 요청하는 작업이다. 새 데이터 디렉터리에 검증된 전체 스키마의 빈 테이블 파일을 생성한다. 기존 데이터 디렉터리·파일을 덮어쓰는 초기화는 하지 않는다.
- 준비 중에는 사용권과 진행 표식을 유지한다. 모든 파일의 존재·헤더·스키마·0행 상태를 확인하고 잔여 정리를 마친 후 표식을 마지막으로 제거한다.
- 생성·검증·정리가 실패한 출력은 준비 완료로 공개하지 않는다. 불완전 출력은 일반 실행에서 차단하고 원인을 진단한다. 초기 준비 명령은 [CLI 계약](cli-contract.md)의 `init`을 따른다.

## 4. 진행 표식·실패·반영 확정

- 변경 대상·작업 종류와 INSERT의 원래 길이 등 복원 판단에 필요한 정보를 진행 표식에 기록한다. 표식은 신규 생성하고 기존 미해결 표식을 덮어쓰지 않는다.
- 원본을 변경하기 **전에** 표식을 기록→`FlushFileBuffers`→handle 종료 순서로 확보한다. 표식 준비 실패 시 원본을 변경하지 않는다.
- 원본 변경 전 필요한 검증·직렬화·처리 건수·성공 결과 메모리 준비를 마친다. 반영 확정 뒤 메모리 할당·출력 실패를 이유로 SQL을 미반영 실패라고 보고하지 않는다.
- 정상 복원 가능한 실패는 문장 전체 변경을 취소하고 이를 확인한다. 복원 실패·상태 확인 실패·예상 밖 파일 상태는 세션 중단·파일 보존·진행 표식 유지로 처리한다.
- 미해결 표식이 남으면 재시작도 차단한다. 파일 형식이 정상이라는 이유만으로 문장 전체 반영 여부를 추론하지 않는다. 수동 복구 판단과 자동 복구 도구는 별개이며 후자는 이번 범위에 없다.
- 반영 확정 뒤 임시/백업 정리 또는 표식 삭제가 실패하면 **SQL 성공과 affected_rows를 유지**하고 저장 정리 오류와 세션 중단을 별도로 보고한다. 해당 SQL을 되돌리거나 자동 재실행하지 않는다. 파일의 뒤 SQL도 실행하지 않는다.
- 잔여 파일 정리 완료 후 진행 표식을 마지막으로 제거한다. 진단은 반영 여부·복원 여부·작업 단계·경로와 원인을 구분한다. I/O와 자원 부족을 구분하고 불명 상태·위치를 꾸며 내지 않는다. 진단 형식·종료 코드·관리 명령은 [CLI 계약](cli-contract.md)을 따른다.

## 5. INSERT 추가 쓰기

1. 문장 전체의 이름·타입·컬럼 수·ID·문장 내부/기존 ID 중복을 검증하고 추가할 레코드들을 준비한다. 준비용 임시 파일을 사용할 수 있지만 원본은 아직 바꾸지 않는다.
2. 유효 원본의 길이 L을 기록하고 진행 표식을 확보한다. 원본에 대한 성공 확정 전 변경은 EOF 추가뿐이다.
3. 준비한 레코드 전체를 추가한다. 부분 write도 처리하며 요청한 전체 바이트 기록과 `FlushFileBuffers` 성공을 확인한다. 여기까지 성공하면 INSERT 반영 확정이다.
4. 확정 전 실패하면 파일 위치를 L로 옮기고 `SetEndOfFile`로 복원한 후 flush·길이 확인을 한다. 복원 완료면 해당 INSERT는 실패·추가 0행이며 기존 데이터는 유지한다.
5. 길이 복원·flush·확인이 실패하면 §4의 중단 상태로 전환한다. 복원 API가 항상 성공한다고 가정하지 않는다.

길이 복원은 앞부분을 바꾸지 않는 불변식에 의존한다. 추가 쓰기는 전체 재쓰기를 줄이지만 ID 중복 검사를 위한 전체 읽기 비용까지 없애지는 않는다. 실제 성능은 미측정이다.

## 6. UPDATE·DELETE 임시 완성본 교체

1. 변경 전 행을 읽어 같은 데이터 디렉터리의 신규 임시 파일에 완성본을 기록한다. SET 우변은 기존 SQL 계약의 old row 기준이며 후반 오버플로도 교체 전 문장 전체 실패다.
2. 결과·자원 준비를 완료하고 임시 파일을 flush한다. 원본 읽기 handle과 임시 파일 작성 handle을 모두 종료한 뒤 교체한다.
3. `ReplaceFileW(main, temp, backup, ...)`에 백업 경로를 지정한다. 성공 반환이 반영 확정이다. 이후 정리 실패는 §4의 반영 후 정리 오류다.

| 실패 상태 | 처리 계약 |
|---|---|
| 1175 `ERROR_UNABLE_TO_REMOVE_REPLACED` | 원이름 유지 상태를 확인하고 원본 유지·임시 정리 |
| 1176 `ERROR_UNABLE_TO_MOVE_REPLACEMENT` | 백업을 지정한 전제의 원이름 유지 상태를 확인하고 원본 유지·임시 정리 |
| 1177 `ERROR_UNABLE_TO_MOVE_REPLACEMENT_2` | 원본이 백업 이름으로 이동한 상태를 확인하고 백업→main 복원 |
| 그 밖의 실패 | 문서화된 원이름 유지 상태를 확인한다. 실패 반환만 보고 원본 불변으로 추정하지 않음 |

- 1177 복원은 `MoveFileExW`의 덮어쓰기·다른 볼륨 복사를 허용하지 않는 이동을 사용한다. 예상 밖 main이 있으면 지우지 말고 중단한다.
- 복원·상태 확인 실패는 파일·표식을 보존하고 재시작을 차단한다. 지원되지 않는 `REPLACEFILE_WRITE_THROUGH`를 내구성 근거로 사용하지 않는다.
- 원자성은 정상적으로 처리 가능한 실패에서 문장 단위다. 파일 전체 SQL 트랜잭션, 장치 고장·강제 종료·전원 차단 복구를 보장하는 프로토콜로 해석하지 않는다.

근거: Microsoft의 [ReplaceFileW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-replacefilew), [MoveFileExW](https://learn.microsoft.com/en-us/windows/win32/api/winbase/nf-winbase-movefileexw), [SetEndOfFile](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-setendoffile), [FlushFileBuffers](https://learn.microsoft.com/en-us/windows/win32/api/fileapi/nf-fileapi-flushfilebuffers). 이는 설계 근거이며 실제 Windows API 검증 결과가 아니다.

## 7. 명시적 스키마 변환

- 일반 실행에서 스키마가 달라지면 거절한다. 변환은 사용자가 요청하는 별도 관리 작업이며 일반 SQL의 암묵적 타입 변환 규칙을 바꾸지 않는다.
- 논리 입력은 원본 데이터 디렉터리·검증된 새 외부 스키마·명시적 컬럼 매핑·삭제 목록·새 출력 디렉터리다. 원본 정의는 각 데이터 파일 헤더에서 읽으므로 이전 외부 스키마 JSON을 별도 필수 입력으로 요구하지 않는다.
- 원본 사용권을 읽기·검증·복사·변환 전체 동안 유지한다. 원본 파일과 원본 스키마 JSON을 바꾸지 않는다. 새 스키마 JSON도 자동 수정하지 않는다.
- 출력은 원본과 겹치지 않는 신규 디렉터리다. 기존 출력 파일을 덮어쓰지 않는다. 진행 표식을 만들고 전체 결과가 검증될 때까지 일반 실행을 차단한다.
- 원본 헤더에서 얻은 테이블 집합과 새 스키마의 집합은 이름을 접어 동일해야 한다. 테이블 추가·제외·이름 변경은 거절한다.
- 새 스키마 전체 테이블을 대상으로 정의가 같고 해결된 매핑도 항등인 파일만 복사한다. 명시적 비항등 매핑·추가·삭제·타입·순서 변경 중 하나라도 있으면 변환한다. 따라서 동일 스키마의 컬럼 값 교환도 복사로 건너뛰지 않는다. 대소문자만 다른 정의는 호환으로 비교한다.

### 컬럼 매핑

- 같은 접은 이름은 기본적으로 같은 컬럼에 대응한다. 이름 변경은 대상 컬럼→원본 컬럼 매핑을 사용자가 명시한다. 명시적 매핑은 기본 대응보다 우선한다.
- 대응은 일대일이다. 없는 컬럼 참조·중복 대상·한 원본의 중복 사용·사용되지 않은 매핑 항목은 거절한다.
- 대응되지 않는 새 비ID 컬럼은 NULL로 채운다. 사용하지 않는 원본 컬럼은 전부 삭제 목록에 명시해야 한다. 사용 중인 컬럼·없는 컬럼·중복 항목을 삭제 목록에 넣으면 거절한다.
- `id`는 기존 `id`에 대응해야 하며 이름의 접은 값·INT64 타입·값을 유지한다. 위치 변경과 대소문자 표기 변경은 허용하되 삭제·새 값 생성·다른 컬럼 대응은 금지한다.
- 컬럼 순서는 새 스키마를 따른다. 값의 보존과 순서 변경은 구분하며 별도 상수·계산식·기본값 기능을 매핑에 추가하지 않는다.

### 타입 변환과 완료

| 원본→대상 | 계약 |
|---|---|
| 같은 타입 | 값을 그대로 보존 |
| INT64→TEXT | 십진수 문자열. 양수의 `+`와 불필요한 앞자리 0 없음. 0은 `0` |
| TEXT→INT64 | 양끝의 ASCII SP·TAB·CR·LF만 제거한 뒤 `[+-]?[0-9]+`와 INT64 전체 범위 검사 |
| NULL→다른 타입 | NULL 유지. 숫자 파싱을 수행하지 않음 |

- TEXT의 내부 공백·빈 문자열·공백뿐인 값·소수·지수·16진수·범위 초과는 실패다. VT·FF·Unicode 공백을 제거하지 않는다. 앞자리 0·`+`·`-0`은 십진수 문법에 맞으면 수치로 해석한다.
- 원본도 모든 행·ID 제약을 검증한다. 하나라도 잘못된 원본·매핑·변환 값·자원/쓰기 오류가 있으면 변환 작업 전체 실패이며 원본은 보존한다.
- 성공 공개 전 새 디렉터리 전체 파일의 존재·헤더 호환·행·ID 제약과 작업 잔여 정리를 확인한다. 모든 파일이 끝나기 전 일부 테이블만 준비 완료로 공개하지 않는다.
- 완료 뒤 표식을 마지막으로 제거한다. 실패 출력은 일반 실행에서 차단하고 자동으로 새 경로에 전환하지 않는다. 사용자가 새 스키마·새 데이터 디렉터리를 지정해 실행한다.

## 8. Phase 연결과 검증 한계

- Phase 2는 기존 SQL을 유지하고 메모리 B+ 트리를 연결한다. 재작성·변환 후 수정되지 않은 행의 물리 위치도 바뀔 수 있으므로 이전 위치를 그대로 사용하지 않는 일관성 요구를 남긴다. 구체 위치 표현·갱신·재구축 알고리즘은 Phase 2에서 정한다.
- 100만 건 적재와 인덱스/선형 조회 비교는 한 DBMS 프로세스에서 수행한다. 현재 처리량·배속을 주장하지 않는다.
- Phase 3은 서버 프로세스 하나의 스레드 풀이 여러 클라이언트 요청을 받아 엔진을 공유한다. 프로세스 사용권은 이 구성과 양립하며 파일·인덱스 변경은 엔진 내부에서 동기화한다. 잠금 세부와 API·프로토콜은 해당 Phase에서 정한다.
- 현재 산출물은 계약과 GWT다. C 구현·자동 테스트·바이너리 roundtrip·실패 주입·프로세스 잠금·마이그레이션·Windows API 실행 검사는 전부 미실행이다. CLI 인자·표시·종료 코드는 [CLI 계약](cli-contract.md)에 확정했다. 실제 C 구현과 도구 검증·하네스 연결은 후속 작업이다.
